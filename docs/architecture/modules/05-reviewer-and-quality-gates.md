# 05. Reviewer 与质量门禁

## 5.1 评审模型

正文 proposal 的评审采用三层结构：

1. 规则门禁。
2. 语义门禁。
3. 100 分制加权评分。

通过条件：

- 无未豁免硬失败。
- 总分不低于 `85`。
- 任一评分维度不低于 `75`。

补充规则：`文风去 AI 味` 采用“规则束 + 模型证据”组合，而不是只靠黑名单或只靠模型主观打分。

## 5.2 硬失败清单

| 硬失败项 | 检测方式 | 说明 |
| --- | --- | --- |
| 禁词命中 | 规则 | 命中项目级黑名单词组 |
| 段落长度违规 | 规则 | 普通叙述段明显偏离目标排版密度 |
| 连续说明文超标 | 规则 + 语义 | 长段解释盖过叙事推进 |
| 角色动机漂移 | 语义 | 行为与既定核心动机冲突 |
| 科技树越级 | 规则 + 语义 | 当前阶段无法合法触发的技术效果 |
| 伏笔回收冲突 | 规则 + 语义 | 与既有 clue 状态或因果链冲突 |
| 细纲结构漂移 | 规则 + 语义 | 先检查 `scene`、`emotionCurve`、`clue plan`、`chapterType` 等硬结构，再用语义分析补充说明结构性偏离 |
| 末段无钩子 | 语义 | 结尾没有有效悬念、升级或反转 |
| 爽点释放不足 | 语义 | 反制与回报没有形成有效兑现 |
| 没有有效压迫段 | 语义 | 情绪曲线缺少承压节点 |
| 没有明显强度上扬 | 语义 | 整章曲线过平 |
| 中段节奏塌陷 | 语义 | 中部场景长时间重复或无推进 |

## 5.3 评分维度与默认权重

| 维度 | 权重 |
| --- | --- |
| 文风去 AI 味 | 20 |
| 网文节奏 | 18 |
| 情绪曲线 | 18 |
| 角色一致性 | 12 |
| 设定/科技一致性 | 12 |
| 伏笔与因果 | 10 |
| 可读性与排版 | 5 |
| 语言质感 | 5 |

总计 `100`。

## 5.4 工件级评分策略

### 正文草稿

- 使用完整 100 分制。
- 要求总分线和单维线同时满足。

### 单章细纲

- 使用简化评分。
- 重点检查章节类型、情绪曲线、伏笔配额、角色逻辑、结尾钩子。

### 分卷大纲

- 使用简化评分。
- 重点检查卷目标、阶段推进、关键回收计划、章节类型序列的可持续性。

### 状态更新提案

- 以结构化校验和差异审查为主。
- 一般不走完整 100 分制。

## 5.5 规则默认值

以下默认值用于 V1 起步，可在 `state/reviewer/` 结构化规则和 `prompts/` 指导模板中调整：

- 普通叙述段目标长度：`50-150` 字。
- 正文目标字数由章节类型决定，默认 `2500-4000` 字。
- 单次自动重写上限：`2` 轮。
- 正文上下文历史窗口：最近 `3` 章原文。

补充规则：黑名单、阈值、taxonomy、override 资格等机器强依赖规则进入 `state/reviewer/`；文风与改写指导保留在 `prompts/`。

## 5.6 豁免机制

### 允许豁免的情况

- 硬失败作者明确接受风险。
- 总分或单维低于门槛，但作者决定继续推进。

### 不允许豁免的情况

- canonical schema 解析失败。
- 稳定引用不存在或 ID 冲突。
- 状态机非法迁移。
- 关键依赖缺失导致 canonical 会进入坏状态。
- `outline-structure-drift`。
- `tech-tree-violation`。
- `clue-payoff-conflict`。

### 豁免必须记录

- `overrideReason`
- `overrideBy`
- `relatedRunId`
- `failedChecks`
- `scoreSnapshot`
- `timestamp`

规则：豁免是一种显式审计动作，不得静默通过；`OverrideAudit` 作为独立、不可变的审计实体持久化，并由 proposal 通过 `overrideAuditId` 引用。

## 5.7 输出契约

Reviewer 必须输出结构化结果，而不是纯自然语言评论。最小输出包括：

- `approved`
- `hardFailures[]`
- `dimensionScores{}`
- `totalScore`
- `rewriteDirectives[]`
- `overrideEligible`

自然语言说明可以存在，但必须附着在结构化结果之上。

补充规则：`ReviewerResult` 作为独立、不可变的审计实体持久化；proposal 自身只保留 `latestReviewResultId` 这类轻量引用。

## 5.8 手工修改后的评审新鲜度

- 作者手工修改已批准的 `chapter-outline` 或 `chapter-manuscript` 后，旧的 Reviewer 结果立即失去新鲜度。
- 这种“review 已过期”不写入 canonical 主状态机，而是作为独立 derived 风险标记展示。
- 系统应异步触发 synthetic review，以重新评估手工修改后的内容。
- 如果 synthetic review 检出不可豁免错误，工件仍保留为 canonical，但所有依赖该工件的自动流程必须被阻断，直到问题修复并重新通过检查。
